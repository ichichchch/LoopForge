模块按清晰的四层组织，依赖方向自上而下单向收敛：
- 表现层 `httpapi`：基于 gin-gonic/gin 的 HTTP API 入口，通过 `Server` 聚合各业务 handler（assistant/issues/runs/schedule/mcp/browser 等），共享依赖集中在 `deps` 结构体，并由 `New/NewWithNotifications` 装配。
- 领域模型层 `domain`：纯 Go 结构体定义所有业务实体（Run、Assistant、Issue、Workflow、Space 等），不含任何存储或网络逻辑，被上层 httpapi 和中间层 engine/repo 共同消费。
- 执行编排层 `engine` + `runner`：`engine.Engine` 负责 Run 生命周期、节点调度、沙箱/工作区协调；`runner` 是独立的 CLI Runner 客户端，通过 RPC 协议驱动真实进程执行，二者通过 `runtime.Manager` 管理沙箱。
- 持久化层 `repo`：基于 gorm.io/gorm 的 MySQL 生产实现（测试用内嵌 sqlite），以 `Store` 组合多个领域 Repo（AssistantRepo、RunsRepo、IssuesRepo 等），跨领域引用在 `newStore` 中一次性注入。

横向能力作为独立包提供：`auth`（用户认证）、`notification`（通知分发）、`knowledge`（知识检索）、`preview`（预览服务）、`schedule`（定时任务）、`tracker`（代码同步）、`observability`（OTLP 观测）、`mcpclient`/`mcpserver`（MCP 双向通信）、`gitwork`（Git 操作）、`gongfeng`（内部 GitLab 封装）、`cronexpr`、`procwatch`、`managedcli`、`runeval`、`botinteraction`、`application`、`config`、`gatemcp`、`runtime`（浏览器/CLI 运行时）等。

依赖注入采用“指针字段回填”模式：`httpapi.New` 构造 `deps` 后反向回调 `engine`（如 `MergeIntoBranch`、`WorkspaceCheckpointTransport`、`SetRunnerDispatchNotify`），避免循环依赖。
